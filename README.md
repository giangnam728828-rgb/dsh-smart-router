# dsh-smart-router · 智能路由

> DeepSeek Harness 插件：**每轮自动**把「可能相关的技能 + 插件能力」送到模型面前，
> 写明判断规矩，然后把**用不用、用哪个**的决定权留给模型。
>
> 零依赖、零模型下载、零向量库。装上是秒级的，跑起来是零成本的。

---

## 它解决什么

两件事，插件都替你做：

1. **技能不再靠运气被想起来** —— 每轮开头给你一份按当前指令收窄过的候选，
   每条都带「为什么它出现在这里」的字面证据。
2. **插件能力第一次变得可见** —— 已安装的插件、它们的用途、本轮的工具有哪些族，
   都会出现在同一块提示里。此前模型只能看到工具名和一句参数说明，
   根本不知道「哪个插件负责哪件事」。

## 它**不**做什么（这是重点）

- **不替你选。** 候选不是命令，判定权始终在模型手里。
- **不注入技能正文。** 正文永远由模型自己调 `skill` 工具去取。
- **不用阈值做判定。** 没有 `minScore` / `zThreshold` 那种「过线就强行注入」的东西。
- **不硬凑。** 一条都对不上就什么都不发 —— 空手比给错强。

---

## 为什么不是「用向量算相似度」

这是本仓库与前身（`lau4tin1/dsh-skill-router`）最根本的分歧。

前身的做法是：`bge-m3` 把任务编码成 1024 维向量 → 与技能向量算余弦 →
`z >= 2.5` 且 `s >= 0.05` 就选中 → **直接把技能正文注入对话**。

它的作者自己在代码注释里记下了三个事实：

| 事实 | 后果 |
|---|---|
| 中文「项目进度报告」类真实匹配只有 0.10~0.13 | 达不到阈值，**永远不会被注入** |
| 阈值是在 24 个技能的语料上标定的 | 换语料就失效 |
| 543MB 的 ONNX 模型只为分辨几十个技能 | 严重的资源浪费 |

更关键的是方向错了：**它是用向量替代判断，不是辅助判断。**
一旦过线，正文就被塞进对话 —— 模型失去了说「这个技能其实不合适」的机会。

这个仓库反过来做：

> **打分只用来把候选从 N 个收窄到 3 个；「该不该用」永远留给模型。**

收窄用字面重合（中英都支持），因为它便宜、确定、无需标定、也不会因为
换了个语料就整体失效。收窄错了怎么办？不会 —— 它只是把明显不相干的滤掉，
真正的判断还在后面。

## 用法

### 作为插件安装（推荐）

```bash
# 在 profile 目录里把它当本地 bundle 装上
dsh plugin add /path/to/dsh-smart-router
```

或者在 Harness 的插件页里「从本地目录安装」，选中本仓库根目录。

装完之后**什么都不用做** —— 它会自己开始工作，因为：

```
apply(ctx) ──▶ ctx.on('agent/pre-step', ...)
                 ↑
        每一轮模型开口之前，这里都会先跑一次
```

### 配置

全部可选项，写在 profile 的 `cordis.patch.yml`（或插件页的配置面板）：

```yaml
- id: smart-router
  config:
    enabled: true
    maxCandidates: 3      # 每轮最多几个技能候选；给太多等于没给
    minScore: 0.02        # 只滤掉明显不相干的，不参与「该不该用」的判定
    includePlugins: true  # 列出已装插件及其用途
    pluginsLimit: 8
    includeToolFamilies: true
    familiesLimit: 10
    debug: false          # 打开后写 ~/.dsh/smart-router/activity.jsonl
```

## 「插件怎么自己主动用？」「技能为什么不行？」

这是设计里最容易被问、也最值得说清楚的一点。

**技能（skill）不可能主动生效。** 它不是代码，是一段说明书：没有执行上下文、
没有事件、没有生命周期，只能被人或模型「翻开」。指望技能自己触发，
等于指望一本书自己翻页 —— 这不是实现缺陷，是它的定义。

**插件可以。** `apply(ctx)` 是宿主在加载时调用的真实函数，它拿到的是完整的
Cordis 上下文：能注册工具、能监听事件、能挂系统提示。所以「每轮自动发生」
这件事，只有插件做得出来。

于是本仓库的分工是：

```
插件（主动）                         技能（被动）
─────────────                        ─────────────
每轮 pre-step 自动运行                被调用时才展开
推送候选 + 规矩                       提供具体的做法
决定「把什么摆到桌面上」              决定「这件事具体怎么做」
```

**驱动者与被驱动者，不是二选一。** 想要「自己会动的路由」，就必须是插件；
而它路由出去的东西，仍然可以是技能。

## 注入长什么样

一个会话里，静态块只出现一次：

```xml
<skill_router>
<routing_rules>
1. 这一块是自动生成的候选清单，不是命令，也不代表任何一条必须被使用。
2. 判断权在你：只有这次任务确实落在某条描述里，才用 skill 工具加载它的正文；不匹配就不要加载。
3. 不要为了「保险」把候选全部加载；也不要为了用而用 —— 没有合适的就直接按自己的方式做。
4. 同一个技能在整个会话里加载一次就够了。
</routing_rules>

已装插件（能力的来源；这些不是技能，不要用 skill 工具去加载）：
- 技能管理（@michengai/dsh-skills-manager）— 统一加载并安全管理本机 Agent Skills
- 插件市场（dshmarket）— 浏览和安装插件

工具族（工具名是按族命名的基础设施，用到时直接调，不需要先加载技能）：
- android（42 个）— 真实触控点击实体主屏
- schedule（4 个）— 创建定时任务
</skill_router>
```

之后每轮按需给候选，同样的一组不重复：

```xml
<skill_router>
<turn_candidates total_indexed="6">
本轮任务：帮我把两个 PDF 合并成一个文件

字面重合度最高的技能（只是候选；不匹配就忽略）：
- pdf-tools — 合并、拆分 PDF 文件（字面重合：pdf、合并）

要用的，调用 skill 工具并传上面那个精确名字；不用的不必解释。
</turn_candidates>
</skill_router>
```

## 开发

```bash
node --test        # 36 个用例：分词、打分、收窄、渲染、配置、整轮模拟
```

模块划分（每一层都能单独测）：

| 文件 | 职责 |
|---|---|
| `lib/route.js` | 纯计算：分词、打分、收窄、工具归族。无 IO。 |
| `lib/render.js` | 纯渲染：把候选和规矩拼成要注入的文本。 |
| `lib/plugins.js` | 只读：从 profile 读出已装插件与用途。 |
| `lib/config.js` | 配置归一化 + 「哪些消息算用户任务」。 |
| `lib/log.js` | 可选诊断日志，失败即静默。 |
| `lib/plugin.js` | 唯一接触框架的地方：挂 `agent/pre-step`，串起上面几层。 |

### 扩展点

- **加技能**：不用改代码。技能注册进 `ctx.skills` 之后，下一轮就会被索引到。
- **加插件**：不用改代码。装进 profile 后，静态块会自动带上它的元数据。
- **改判断风格**：改 `lib/render.js` 里的 `RULES`；那是模型每轮都会读到的规矩。
- **换收窄算法**：只改 `lib/route.js`，接口就三个函数，`index.js` 不关心内部实现。

### 失败姿态

全链路 fail-open：任何一步抛错都降级成「这一轮没有提示」，绝不阻断用户这一轮。
也刻意不写模块级 `inject` —— 硬依赖缺失会让 entry 永远 pending，
进而拖垮整棵插件树（`dsh-device-shell-guide` 0.1.9 出过这个事故）。

## 与其他同名项目的区别

GitHub 上有好几个 `dsh-skill-router`，容易混淆：

| 仓库 | 它是什么 |
|---|---|
| `ZiYuan258/dsh-skill-router` | 关键词检索 + `skill_search`/`skill_load` 工具，明写「Not an auto-inject router」 |
| `lau4tin1/dsh-skill-router` | **本仓库的前身**：bge-m3 向量 + 阈值 + 正文注入 |
| **本仓库** | 去掉向量与阈值，改为「收窄候选 + 模型判定」；并补上插件能力路由 |
